# F5 单位与职位检索知识库扩展规划

- 日期：2026-09-11
- 状态：**阶段 0 与阶段 1 已交付**（2026-09-12）；阶段 2–4 未开始，尚未接入任何外部数据源
- 范围：单位发现、职位检索、求职信增强、申请跟踪

## 1. 当前能力与边界

当前 F5 只完成以下闭环：

1. 用户手动填写目标公司和目标职位。
2. 服务读取该会话最新一次 F1 简历诊断，从已验证的简历证据中生成求职信候选。
3. 用户确认后，将公司、职位、求职信和固定状态保存为申请记录。
4. 用户可以查看或删除本人名下的申请记录。

当前没有单位或职位搜索接口，没有企业、事业单位、学校、医院、研究院、社会组织或实时职位数据集，也不会核验用户填写的单位主体、招聘状态或职位真伪。现有面经知识库只有通用面试问答，与 F5 单位检索无数据关联。大语言模型不得被当作企业事实来源。

## 2. 产品目标与非目标

### 2.1 产品目标

- 支持已知名称检索：公司简称、曾用名、英文名、拼音、缩写和少量错别字仍能召回正确主体。
- 支持抽象发现：例如“厦门做海洋遥感、接受应届生的研究院或中小企业”。
- 同时覆盖常见企业和小众单位，不以知名度或广告预算作为主要排序依据。
- 每条单位与职位结果展示来源、核验时间、有效状态和跳转原页面。
- 选定单位和职位后，才把获授权的事实、JD 与 F1/F2 证据用于求职信生成。
- 保留手动输入作为数据源不可用时的明确降级路径，但标记为“未经平台核验”。

### 2.2 非目标

- 不自动投递简历，不代替用户接受招聘条款或对外发送消息。
- 不抓取或复制未取得授权的招聘平台、企业数据库和个人评价内容。
- 不用模型生成不存在的单位、职位、薪资、招聘状态或企业事实。
- 不根据年龄、性别、民族、健康、家庭等敏感属性推荐或排除单位。

## 3. 数据源准入要求

单位主体与实时职位是两类不同数据，不能用一个静态问答知识库替代。

| 数据层 | 首选来源 | 必须满足的条件 | 不满足时的处理 |
| --- | --- | --- | --- |
| 企业主体 | 获授权的工商数据 API；权威登记渠道 | 明确允许本产品查询、缓存及向终端用户展示所需字段 | 不接入；不得批量抓取查询网页 |
| 高校等单位 | 主管部门发布的公开名单 | 记录版本、发布日期、原始链接与允许的复用范围 | 仅提供跳转，不复制受限字段 |
| 事业单位、医院、研究院、社会组织 | 相应主管部门目录或获授权聚合数据 | 能区分主体类型、状态和更新时间 | 标记未覆盖，不由模型补齐 |
| 实时职位 | 单位招聘官网、授权职位数据源或用户提供的 JD/链接 | 允许展示摘要或字段；保留原职位链接和失效规则 | 只接受用户手动输入并标记未核验 |
| 单位介绍与动态 | 单位官网及获授权公开信息 | 能追溯到具体页面和采集时间 | 不进入事实字段和硬排序 |

签约任何商业 API 前必须确认终端展示、缓存期限、派生数据、批量调用和删除纠错权利。普通“内部查询”授权不能默认用于公开的求职产品。

## 4. 双索引架构

### 4.1 单位实体索引

负责回答“这个单位是谁、是什么类型、在哪里、是否仍正常存在”。建议表：

- `organizations`：规范名称、机构类型、地区、行业、统一标识、状态、官网域名、来源、来源主键、来源更新时间、最后核验时间。
- `organization_aliases`：简称、旧名、英文名、拼音、缩写及规范化值。
- `organization_profiles`：经授权的业务方向、产品、技术领域、单位规模区间和内容哈希。
- `source_snapshots`：来源链接、获取时间、授权范围、内容哈希和解析版本。

### 4.2 职位时效索引

负责回答“该单位现在是否在招、岗位是否仍有效”。建议表：

- `job_postings`：单位 ID、外部职位 ID、职位名称、地点、岗位类型、技能标签、允许保存的 JD 摘要、原页面链接、发布时间、截止时间、最后发现时间和来源。
- `job_posting_versions`：职位关键字段变化与内容哈希，避免重复入库并支持纠错审计。
- `job_embeddings`：仅对获授权且内容变化的单位/职位描述生成向量。

### 4.3 申请记录扩展

现有 `applications` 后续增加：

- `organization_id`、`job_posting_id`、`source_url`
- `stage`：准备、已投递、笔试、面试、Offer、拒绝、撤回
- `applied_at`、`next_action_at`、`updated_at`
- `verification_state`：已核验、用户手填、数据已过期

## 5. 检索与排序

### 5.1 已知名称检索

1. 名称、别名、统一标识精确匹配。
2. 中文规范化、拼音、首字母与常见后缀归一化。
3. PostgreSQL `pg_trgm` 或等价编辑距离召回一至两个错字的候选。
4. 地区、机构类型和经营状态消歧。
5. 低置信度时列出候选让用户确认，不自动认定主体。

### 5.2 抽象单位发现

1. 将自然语言拆成地点、领域、技能、机构类型、规模、应届/实习和时间约束。
2. 并行进行名称/标签 BM25 与单位简介、职位技能向量召回。
3. 用 RRF 合并候选，再以 F1 简历证据和 F2 岗位要求进行可解释重排。
4. 结果分成“高度匹配”和“小众探索”，通过类型、规模和地域多样化避免只返回头部企业。
5. 本地有效候选不足或最高置信度过低时，按许可调用外部数据源扩展；仍无结果则明确返回未找到。

模型只可以提取结构化检索条件和解释已检索结果，不能直接生成候选单位清单。

## 6. API 与页面流程

建议新增 API：

- `GET /api/organizations/suggest?q=`：名称联想与主体消歧。
- `POST /api/organizations/discover`：自然语言单位发现及筛选。
- `GET /api/organizations/{id}`：主体详情、来源与核验状态。
- `GET /api/organizations/{id}/jobs`：该单位仍有效的职位。
- `PATCH /api/wf07/applications/{id}`：更新申请阶段和下一行动。

F5 页面分成四步：

1. 搜索或手动填写单位。
2. 选择已核验职位或粘贴 JD。
3. 展示“单位事实来源 + 职位来源 + 简历证据”，再生成可编辑求职信。
4. 用户确认后保存，并在申请跟踪中更新阶段。

## 7. 时效、溯源与降级

| 数据 | 建议新鲜度 | 过期处理 |
| --- | --- | --- |
| 单位规范名称、类型、地区 | 30 天；用户选中或投递前按需刷新 | 标记待核验并尝试刷新 |
| 主体存续/经营状态 | 投递前刷新；已收藏主体最长 7 天 | 刷新失败时不宣称状态有效 |
| 实时职位 | 24 小时内刷新 | 到截止日或连续 7 天未再次发现即下线 |
| 单位业务简介 | 7 至 30 天 | 显示来源日期，不用于硬性真实性判断 |
| 单位动态或新闻 | 7 天以内 | 仅作带链接的辅助信息，不作为事实承诺 |

所有返回项必须包含 `source_provider`、`source_url`、`source_updated_at`、`verified_at` 和 `verification_state`。外部服务故障时只能返回仍在有效期内的缓存；过期内容必须显著标识，不能静默当成实时结果。

## 8. 安全与合规

- 所有外部地址经过协议、域名与重定向白名单检查，阻断内网地址、云元数据地址和任意 URL 抓取，防止 SSRF。
- 外部 API 密钥仅保存在服务端环境变量中；按用户和数据源设置分钟、小时和每日预算。
- 查询归一化、长度限制、参数化 SQL、HTML 输出转义，并限制分页大小和深翻页。
- 原始页面不长期落库；只保存授权字段、短摘要、内容哈希和溯源元数据。
- 用户简历、检索偏好和申请记录遵循目的限定与最小必要原则，支持导出、更正和删除。
- 个性化排序展示主要依据，提供非个性化排序及偏好清除入口。
- 单位纠错、冒用、虚假招聘和职位过期应有举报、复核、下架与审计链路。
- 求职信生成必须继续执行简历事实锁，并新增单位事实与 JD 引用检查；生成内容保持待确认且允许用户编辑。

## 9. 分阶段实施与验收

### 阶段 0：能力边界透明化

- 页面明确说明当前不搜索、不核验单位与职位，面经知识库不等于企业库。
- `public/` 与 `docs/` 页面保持一致，并由静态测试锁定。

验收：页面可见、语义清楚、镜像测试通过。

### 阶段 1：内部基础框架

- 建立单位、别名、职位、来源快照与申请阶段表。
- 建立 provider adapter、缓存、错误合同和管理端数据源健康状态。
- 页面保留手动输入，并明确标记未核验。

验收：无外部 API 时不伪造数据；归属隔离、删除闭环和失败降级通过。

### 阶段 2：获授权的单位名称检索

- 接入一个具有终端展示授权的单位数据源。

### 阶段 3：实时职位与抽象发现

- 接入获授权职位来源或单位官网职位连接器。

验收：人工标注的抽象查询集 nDCG@10 不低于 0.75；有效职位中至少 95% 在 24 小时内核验；过期职位泄漏率低于 1%；不存在无来源的模型生成单位。

### 阶段 4：生产运营与成本治理

- 增加数据源延迟、错误率、缓存命中率、单位覆盖率、职位新鲜度和单次检索成本监控。
- 建立纠错、举报、下架、数据源熔断和回滚流程。
- 完成许可审查、隐私影响评估、安全测试和真实用户验收。

验收：P95 本地搜索低于 300ms，外部扩展低于 2s；外部 API 成本有硬预算；数据源故障不会产生虚构或无来源结果。

## 10. 当前阻断与决策点

在实现“全面且小众”的线上单位搜索前，必须先确定：

1. 覆盖地域及单位类型，是否包含港澳台和境外单位。
2. 至少一个允许终端用户展示与必要缓存的数据授权方案。
3. 实时职位来源及其展示、摘要、缓存和跳转权利。
4. 月度外部数据预算、目标搜索量与缓存策略。
5. 单位纠错与虚假招聘复核责任人。

这些决策未完成前，可以先建设内部 schema、provider adapter、检索合同和页面骨架，但不能宣称已经具备全面单位库或实时职位覆盖。
